## 1. 评审结论

### 1.1 缺陷统计

| 等级 | 数量 | 性质 |
|------|------|------|
| **P0** | 6 + **4**（第二轮） | 设计规则在真实代码上不成立 / 不变量缺失 / 业务闭环不完整 / 投递保证缺失 / 代码级数据缺陷 / **多步操作无补偿、事件目录与面积变更未联动**（见 §4A） |
| **P1** | 6 + **6**（第二轮） | 自相矛盾、模块归属错误、接口签名错误 / **链路断裂与缺校验**（见[业务闭环编排设计](./业务闭环编排设计.md) §5） |
| **P2** | 5 + **7**（第二轮） | 文档准确性、术语、校验方式 / **补强项** |

### 1.2 一句话结论

V1.0 的**方向正确**（三层模型、聚合独立、上下文内聚、约束优先于纪律），但**把"分层"写成了理想模型而没有对照真实 import 校验**，导致：

1. 被定义为 L0 的"流程协同"实际有 **5 处**反向依赖，按 V1.0 的 ArchUnit 规则第一天即红；
2. ADR-0019 决策 B 删除了状态白名单后，**审批期互斥出现空洞**——审批中不写占用，`EXCLUDE` 不参与判定，并发超租无任何约束覆盖；
3. 文档自拟 9 条流程，但对照 SRS §4.27，**十三条闭环只有 3 条完整覆盖**；
4. 只读投影依赖进程内 `afterCommit` 事件，**无投递保证**。

另在评审过程中发现 **2 项代码级缺陷**（非文档缺陷），其一会在组合租赁下造成占用永久不收口。

### 1.3 闭环覆盖度

**首轮（以「文档是否建模」为尺子）**：

| 状态 | 数量 | 闭环 |
|------|------|------|
| ✅ 完整建模 | **3** | 1 经营、3 退租、6 处置 |
| ⚠️ 部分建模 | **5** | 2 空置（盘活→招租缺）、4 风险（预警处置状态机缺）、7 占用（解除链缺）、8 业财（对账/凭证/收入确认缺）、9 发票（红冲/勾稽缺） |
| ❌ 未建模 | **5** | 5 监管、10 退款、11 评估、12 通知、13 自用 |

另有两条**跨闭环前置**未建模：合同变更（FR-CON-LC-004）、期初迁移（FR-MIG-*）。

**第二轮（以「代码是否已实现」复核，见 §4A）**：上述 10 条中 **7 条状态机与跨域联动已在代码中实现**，属设计文档滞后；**唯一真实功能缺失**为通知闭环的事件目录只实现 2/8。逐闭环编排规格与 20 项已验证缺口见[业务闭环编排设计](./业务闭环编排设计.md)。

## 2. 评审方法

不看文档"说了什么"，只看它"约束了谁"，用两把可证伪的尺子：

| 尺子 | 具体做法 | 为什么可证伪 |
|------|---------|------------|
| **① 真实依赖关系** | `rg "^import com\.ams\.modules\."` 逐模块提取跨模块 import，与文档的分层表逐条比对 | import 是代码事实，不是设计意图 |
| **② SRS 闭环清单** | 以 §4.27 十三条闭环 + §4.23 二十九个补强闭环为基准，逐条查文档是否有对应编排、上下文归属、一致性策略 | 验收矩阵是需求事实，不是自评 |

辅助证据：`V39`–`V41` 迁移中的约束与视图定义（判断不变量是否真的落地）、`AssetOccupancyService` 的 Javadoc（判断设计意图是否与实现一致）。

**未覆盖维度**（见 §7）：三端交互、权限数据范围、性能、P2 子系统。

## 3. P0 缺陷

### P0-1｜L0「流程协同」不是 L0，五处依赖当场违反自带规则

**现象**：文档 §6.3 定义 `L0 = 流程协同（审批/待办/通知/预警）` 并规定"依赖只能向下"，但真实 import 显示：

| 模块（V1.0 归入 L0） | 真实依赖 | 违反 |
|---|---|---|
| `alert/service/AlertService` | `contract.mapper.ContractMapper`、`billing.mapper.BillMapper` | L0 → L3/L4 |
| `compliance/service/ComplianceService` | `contract.mapper`、`lease.mapper.TenderAnnouncementMapper`、`lease.service.LeaseListingService` | L0 → L3 |
| `plan/service/BusinessPlanService` | `dashboard.service.DashboardService` | L0 → L5（跨 5 层） |
| `opscalendar/service/OpsCalendarService` | `occupation.mapper`、`selfuse.mapper` | L0 → L2 |
| `revitalization`（归 L2）调用 `alert`/`task` | 依赖方向可接受，但佐证"预警"被当公共层用 | — |

**决定性证据**（`AlertService` 主动扫描合同与账单，不是"订阅事件"）：

```9:17:backend/src/main/java/com/ams/modules/alert/service/AlertService.java
import com.ams.modules.asset.entity.Mortgage;
import com.ams.modules.asset.service.CertificateService;
import com.ams.modules.billing.BillStatus;
import com.ams.modules.billing.entity.Bill;
import com.ams.modules.billing.mapper.BillMapper;
import com.ams.modules.contract.ContractStatus;
import com.ams.modules.contract.entity.Contract;
import com.ams.modules.contract.mapper.ContractMapper;
import com.ams.modules.task.entity.Task;
```

`billMapper.selectList(...)`（同文件 :166）、`contractMapper.selectList(...)`（:136/:151）说明预警的**规则本身就是域知识**，不属于公共层。

**影响**：若照 V1.0 规则写 ArchUnit，这 4 个模块第一天即红；若为过门禁而把它们留在 L0，等于作废"依赖方向"这条规则，文档核心收益归零。

**处置（已实施）**：设计 V1.1 §4.1 拆出 **L0 纯能力层**（组织与权限 + 流程与协同），并给出迁移落点：`alert`/`compliance`/`opscalendar` → **L5 风险与合规**，`plan` → **L5 经营计划与督办**；新增 ArchUnit 规则 `l0MustNotTouchBusinessDomain`（error 档）与 §6.2 交互方式 ⑤**依赖倒置**（下层定义接口、上层实现注入），使"提交前查合规"不构成向上依赖。

### P0-2｜审批期无互斥：并发超租没有任何不变量覆盖

**现象**：文档所列 7 条不变量**没有一条**能防住"两个审批同时通过、签约同一单元"。

**证据链**：

1. ADR-0019 决策 B 删除 `LeaseControlStatus.canTransition`，把合法性**全部**交给 `ex_occupancy_unit_no_overlap`；
2. `AssetOccupancyService.occupy` 的 Javadoc 自述：

   > 调用时机：单据**审批通过**时（不是提交时）。审批中占用的面积预留属于合同链路的校验职责（见 `LeaseAreaGroups.AREA_HOLDING`），不进入本表。

3. 因此审批中的合同**不写占用 → 不进入 `EXCLUDE` 判定**，约束根本不参与；
4. `lease`/`selfuse`/`occupation` 服务层的 `assertUnitAvailable` 只是"把冲突转成可读提示"（该 Javadoc 明言"不作为正确性依赖"），且锁在事务提交后释放。

**影响**：并发签约可超租，且数据库不会有任何报错。这是"约束优先于纪律"在**审批期**的空洞——正是 ADR-0019 想要消灭的病根。

**处置（已实施）**：ADR-0020 决策 E + 设计 §10.3 —— **方案 A 预留态**：提交审批即 `occupy(biz_status='reserving', exclusive=true)`，通过转 `active`，驳回/撤回区间收口。`EXCLUDE` 的 `WHERE (exclusive)` 与 `ck_occupancy_type` **均无需修改**（预留是 `biz_status` 不是新类型），成本最低。`LeaseAreaGroups.AREA_HOLDING` 降级为查询视图，消除双份真相。

### P0-3｜十三条闭环仅 3 条完整覆盖

**现象**：文档自拟 9 条流程，与 SRS §4.27 验收矩阵对照后，完整覆盖 3 条（见 §1.3）。缺失的 5 条中，4 条连文档归属都没有（监管、退款、评估、合同变更、期初迁移）。

**影响**：验收要求"十三条闭环全部通过"，而设计文档无法作为闭环实现的依据；§4.23 下二十九个补强闭环（减免调价、预收预交、保证金、盘点、抵押解押、电子签、智能定价、期初迁移…）**一个都没有映射**。

**处置（已实施）**：设计 V1.1 §11.1 新增**十三条闭环映射矩阵**（主导上下文 / 参与上下文 / 编排方式 / 一致性 / 状态），并如实标注 ❌/⚠️；附加两条跨闭环前置（合同变更、期初迁移）。矩阵**未**补齐编排与状态机（评审决议：本轮只补矩阵），⚠️/❌ 项须排期。

### P0-4｜事件无投递保证，只读投影的一致性无结构性支撑

**现象**：文档要求下游用只读投影存 `AssetRef` 快照，靠 `afterCommit` 事件刷新；但 ADR-0013 明确进程内事件、不引入 MQ。提交后崩溃／重启／监听器抛异常，事件**永久丢失**，投影陈旧且无人知晓。文档仅给"一致性作业每日比对"——那是**检测**，不是保证。

```text
主数据事务 commit ──► 进程崩溃 / 监听器异常
                        └── 事件永不投递，下游投影永久陈旧
```

**处置（已实施）**：ADR-0020 决策 F + 设计 §12.4 —— `V44__domain_event_outbox.sql`（发件箱 + `event_consumption` 幂等台账 + 6 类通知模板）、`OutboxStore`（`record` 走 `REQUIRED` 与业务写同事务；`markDone`/`markRetry` 走 `REQUIRES_NEW`，因在 `AFTER_COMMIT` 之后原事务已结束）、`OutboxDispatcher`（`SKIP LOCKED` + 租约领取，避免多实例重复领取且无需新增 `dispatching` 状态）、`EventConsumptionGuard`（走 `REQUIRED` 保证幂等台账与消费效果同事务，并主动校验「必须在事务内调用」以免静默退化为非原子）；验收 SQL ⑧ 要求 `dead = 0`。

**顺带修复**：`DomainEventPublisher` 原用 `@TransactionalEventListener` 的默认 `fallbackExecution=false`，在**无事务**调用点（定时任务、非事务 Service）事件会被**静默丢弃**且无人知晓。改为 `true` 后无事务时立即分发，且发件箱已落行、失败仍可重放。

### P0-5｜【代码缺陷】组合租赁退租只释放一个单元，其余占用永久锁死

**现象**：`AssetOccupancyService.findOpenBySubject` 带 `.last("LIMIT 1")`：

```java
// AssetOccupancyService.findOpenBySubject
return occupancyMapper.selectOne(new LambdaQueryWrapper<AssetOccupancy>()
        .eq(AssetOccupancy::getSubjectType, subjectType)
        .eq(AssetOccupancy::getSubjectId, subjectId)
        .isNull(AssetOccupancy::getDateTo)
        .orderByDesc(AssetOccupancy::getId)
        .last("LIMIT 1"));
```

`releaseBySubject(...)` 与 `markVacating(contractId)` 均基于它实现，因此**只能处理一条占用**。

**影响**：组合租赁（决策 C 下"一合同 N 单元"= N 条 `asset_occupancy` 行）退租后，仅 1 个单元收口，其余 N-1 条 `date_to` 永远为 `NULL`：

- `EXCLUDE` 永久拒绝这些单元的任何新占用 → **单元不可再租**；
- 资产租控派生状态长期显示被占 → 看板/报表失真；
- 退租 Saga 第 2 步实际未完成，后续补偿与对账无依据。

**处置（已实施）**：设计 V1.1 §10.2 将接口改为**按单元释放**（`releaseUnit`）与**按单据释放全部**（`releaseBySubject`），并在 §9.2 明确"一份合同占 N 个单元即写 N 条占用"。ADR-0020 决策 E 后果 5 要求删除 `findOpenBySubject` 的 `LIMIT 1` 假设。**代码已修复**（实现状态与验证证据见 §6.2）。

### P0-6｜【决策引入】派生视图未排除 `reserving` 会造成回归

**现象**：`v_unit_lease_status` 的判定条件是 `CURRENT_DATE <@ daterange(o.date_from, o.date_to, '[)')`，**不过滤 `biz_status`**。决策 E 引入预留行后，一份**尚未批准**但起始日已到（或起始日在过去）的合同，会让单元派生状态显示为 `leased`。

**影响**：决策 E 在修好并发超租的同时，会引入"审批中即显示在租"的展示回归，并可能污染 `v_asset_lease_status_reconcile`（物化列与视图比对）。

**处置（已实施）**：设计 §10.3 列为**必须同步的实现后果 2**，`OccupancyBizStatus` 新增 `RESERVING` 与 `V42` 迁移（派生视图排除 `reserving`）；新增验收 SQL ⑨ 专门校验"派生租控状态不得被 `reserving` 污染"。ADR-0020 风险与缓解首条即为该回归。**已同批交付**（实现状态与验证证据见 §6.2）。

## 4A. 第二轮核对发现（代码 vs 文档覆盖度）

首轮评审以「文档是否建模」为尺子，第二轮以「**代码是否已实现**」复核 10 条 ⚠️/❌ 闭环，发现**重要偏差**：**10 条中有 7 条的状态机与跨域联动已在代码中实现**，文档的 ❌ 会让读者误判为功能缺失。

| 闭环 | 文档标注 | 代码实际 | 结论 |
|------|---------|---------|------|
| 2 空置 | ⚠️ | `RevitalizationTask` + `createOnVacant` + `closeOnLeased` + `escalateLongVacant` | 基本实现 |
| 4 风险 | ⚠️ | `AlertService`：pending/processing/closed/escalated | 基本实现 |
| 5 监管 | ❌ | `ComplianceService` + `RegulationReportService` | **已实现** |
| 7 占用 | ⚠️ | `OccupationService`：draft/approving/occupied/released | **已实现** |
| 8 业财 | ⚠️ | `ReconcileService` 13 方法 + 未达账项 + 月结 | **已实现** |
| 9 发票 | ⚠️ | `InvoiceService`（含勾稽与红冲）+ `InvoiceReconcile` | **已实现** |
| 10 退款 | ❌ | `RefundService` 已串 `reverseAllocation → redFlushByPayment → pushVoucher` | **已实现** |
| 11 评估 | ❌ | `EvaluationService` + `recordResult` 回写评估值/底价 | **已实现** |

**由此新增 4 项 P0 级发现**（均为「设计已定、未落地」或「多步操作无补偿」，详见[业务闭环编排设计](./业务闭环编排设计.md) §5）：
