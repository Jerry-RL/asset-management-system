## 1. 目标、范围与非目标

### 1.1 目标

让以下业务可端到端跑通，且状态只有一个来源：

1. 一个资产**部分出租**、部分空置/自用（分租）；
2. 合同签约时**绑定到计租单元**，账单可回溯到单资产/单单元；
3. 单元可**拆分**（表达分租）与**合并**（撤销误拆）；
4. 资产结构变更后，**租控状态自洽**、分区汇总不重复计数、下游计量口径一致。

### 1.2 明确不在本期范围

| 不做 | 原因 | 何时做 |
|------|------|--------|
| 组合租赁（`lease_bundle`）重构 | 双表达期可容忍，不阻塞分租 | 双表达期收敛阶段 |
| 拆合审批流接入 `ApprovalEngine` | **待产品决策（D3）** | 决策后 |
| `contract_line`（合同行）建模 | 一合同一单元即可支撑分租；多单元场景由组合租赁暂时承担 | `V58+`（ADR-0020 决策 C） |
| 按公司/按域拆服务 | 与 ADR-0002 冲突，当前规模无收益 | P4 |
| 前端完整改版 | 只做本方案验收所需的最小入口 | 随批次 |

### 1.3 关键认知（写在最前面）

> **本期工作量的 70% 不在"拆合"，而在"把合同接上单元与占用"。**
>
> 单元表（`asset_unit`）与占用表（`asset_occupancy`）**已经建好并回填**（V39–V42），但**没有任何合同往里写过数据**：全库 `occupy(...)` 的调用方只有 `OccupationService` / `SelfUseService` / `MigrationService` 三处，不含合同；`contract.asset_unit_id` 在 Java 侧从未被写入。
>
> 因此**拆得再细，合同也看不见**——分租收入拿不到，且合同一生效其状态就会被派生器按"查不到占用"回滚。

## 2. 四条落地原则（不可协商）

### 原则 1：写入与收口**同批交付**

合同占用的 `dateTo` 传 `null`（`AssetOccupancyService` 注释明写*"为空表示无固定期限（在租合同）"*），即**开区间**。而 `v_unit_lease_status` 的判定是 `CURRENT_DATE <@ daterange(date_from, date_to, '[)')` —— 开区间**永远命中**。

所以只写不收口的后果是：

1. 占用行**永不结束** → 派生器把单元/资产**永久判为在租**；
2. 叠加 `EXCLUDE`（`ex_occupancy_unit_no_overlap`，`WHERE exclusive`）→ **该单元永久锁死，再也租不出去**。

**这比不改更糟**（现状只是状态显示错，数据可修、单元还能租）。故：**每加一条占用写入，必须同批交付其收口**，不得分期。

### 原则 2：只读观测先于写入改造

`LeaseStatusDeriver.refreshReconciled`（`:112`）与 `v_asset_lease_status_reconcile` **已实现但全库无调用方**，`platform/job` 下也没有它。因此当前"状态漂移"**既不为零、也不可见**。

先接只读比对（不改数据、不动写入路径、不依赖任何待定决策），把问题的规模变成一个数字——**后续所有排期讨论都应以它为输入**。

### 原则 3：双写过渡，不替换

`activate` 阶段**保留** `leaseControlService.transition(LEASED)` 的同时新增 `occupy`。理由：两者在"占用行存在"时结论一致（派生器算 `leased`，状态机也写 `leased`），**双写期不会产生分歧**，且保留了回退路径。

### 原则 4：逐域灰度、逐域可回滚

每个写入域（合同 / 招租 / 处置 / 退租）独立开关。**禁止**一个 PR 同时切换多个域。回退手段必须是"关开关"，而不是"改回来"。

## 4. 批次详解

### B0 · 只读漂移观测（1–2 人日，零风险，**最先做**）

**目标**：把"状态漂移"从不可见变成可观测的数字。

**改动**

| # | 文件 | 改动 |
|---|------|------|
| 1 | `LeaseStatusDeriver` | 新增**只读**方法 `detectReconcile(int limit)`：内部即 `occupancyMapper.selectReconcile(capped)`（该方法已存在，见 `AssetOccupancyMapper:83-88`），**返回差异列表但不调用 `refresh`**。⚠️ 不可直接复用 `refreshReconciled`——它会**写库** |
| 2 | `ScheduledJobs`（`platform/job`） | 新增 `leaseStatusDriftScan()`，`@Scheduled(cron = "0 30 5 * * *")`（05:30 当前无任务占用）。注入 `LeaseStatusDeriver`，日志输出差异条数 + 前 N 条 `assetNo/stored/derived` |
| 3 | `ScheduledJobs` 构造器 | 注入 `@Value("${ams.lease.drift-alert-threshold:1}") int threshold`，超阈值 `log.error` 触发既有告警通路 |
| 4 | `application.yml` | 新增 `ams.lease.drift-alert-threshold`（默认 1） |

**为什么只读而非直接修数据**：修数据会掩盖"是谁造成漂移"这个更重要的信息。B0 的目的是**取证**，不是治污。

**验收**

- 日志稳定输出漂移条数；
- 人工交叉验证：对**合同已生效（`status='active'`）的资产**统计 `lease_control_status`，其中有多少是 `vacant`——**这个数字就是 D-05 的量化证据**。

**回退**：删除 cron 方法 + 配置项。无 DDL、无写入、零残留。

### B2 · 合同写占用 + 五处收口（8–10 人日，**核心批次**）

#### B2.0 前置设计：合同生命周期 → 占用区间语义（**必须先评审**）

这一步不做完，B2.1~B2.5 会各写各的，区间语义必然分叉。

```text
合同状态            →  占用行
────────────────────────────────────────────────────────────────
DRAFT                :  无
APPROVING            :  （若启用决策 E）reserve(unit, [startDate, endDate), biz=reserving)
                        本期默认不启用，见 §9 D1
ACTIVE               :  occupy(unit, [startDate, endDate), biz=active)
RENEWABLE / EXPIRING :  不变（租户仍在，占用继续）
──────────────────────── 以下为五个终止态，每个都必须收口 ────────
驳回 / 撤回           :  cancelReservation （若已 reserve）
退租完成              :  releaseBySubject('contract', id, 实际腾空日)
终止 / 作废           :  releaseBySubject('contract', id, 终止日)
续签 / 转租           :  收口旧合同占用于 [新合同生效日)；新合同重新 occupy
合同到期（转 EXPIRED）:  收口占用于 endDate        ← 见 B2.5，本次新增发现
```

**区间取值约定**：`date_from = contract.startDate`，`date_to = contract.endDate`（`daterange` 为 `[)`，右开，正好表达"租期最后一天仍占用"）。

#### B2.1 生效时写占用

| 文件 | 改动 |
|------|------|
| `ContractService.activate`（`:200`） | 开关开启时调用 `assetOccupancyService.occupy(unitId, OccupancyType.CONTRACT, "contract", id, startDate, endDate, OccupancyBizStatus.ACTIVE, remark)`。**保留** `leaseControlService.transition(LEASED)`（原则 3） |
| `ContractService` 构造器 | 注入 `AssetOccupancyService`（**当前无此依赖**） |

新增开关 `ams.occupancy.contract-dual-write`（默认 `false`）。

#### B2.2 收口一处：审批驳回 / 撤回

| 文件 | 现状 | 改为 |
|------|------|------|
| `ContractService.onApprovalCompleted`（`:162`） | 驳回分支**仅** `setStatus(DRAFT)` + `updateById` | 追加 `occupancyService.cancelReservation("contract", id, today, remark)` |

> 参照 `OccupationService` / `SelfUseService` 已交付的同构实现（改造清单触点 5/6）。

#### B2.3 收口两处：退租完成 / 终止作废

| 文件 | 现状 | 改为 |
|------|------|------|
| `VacateService`（`:263`） | 仅 `transition(VACANT)` | 追加 `releaseBySubject("contract", contractId, 实际腾空日)` |
| `ContractService.voidContract` 等终止路径 | 仅 `contractVersionService.snapshot` | 追加 `releaseBySubject("contract", id, 终止日)` |

#### B2.4 收口三处：续签 / 转租

| 文件 | 现状 | 风险 |
|------|------|------|
| `ContractService.renew`（`:215`） | **不改旧合同状态**——旧合同留在 `RENEWABLE`/`EXPIRING`，二者均在 `LeaseAreaGroups.OCCUPYING` 内；新合同 `startDate = old.endDate + 1` | 旧占用为**开区间**，新占用起点落在旧区间内 → **必然重叠** → `EXCLUDE` 拒绝 → **续签无法生效** |
| `ContractService.transfer`（`:243`） | 新草稿合同，旧合同保持 `ACTIVE` | 新合同激活时旧合同仍 `ACTIVE` → 同样重叠 |

**改法**：新合同**进入 ACTIVE 的那一刻**，在同一事务内先收口旧合同占用：

```text
activate(新合同):
  1) if (新合同.parentContractId != null):
       releaseBySubject('contract', parentContractId, 新合同.startDate)
  2) occupy(新合同.assetUnitId, 'contract', 'contract', 新合同.id,
            startDate, endDate, ACTIVE, remark)
  3) transition(LEASED)                      // 原则 3：双写
```

> ⚠️ **`transfer` 有一个额外语义待确认**：转租期间"原合同保持生效直至新合同激活"是设计意图（改造清单触点 8 引述），意味着**过渡期两合同共用同一单元**。启用占用后该过渡期**无法用互斥表达**。见 §9 D2。

#### B2.5 收口四处：合同到期（**本次核查新增发现**）

**证据**：`v_unit_lease_status`（`V42:29-73`）**完全不引用 `contract` 表**——它只读 `asset_occupancy`、`lease_listing` 与 `asset.lifecycle_status`。因此"合同状态"与"派生租控状态"之间**唯一的耦合就是占用行**。

**推论**：`ScheduledJobs.contractExpiryScan`（每日 04:00）把合同从 `ACTIVE`/`RENEWABLE` 翻为 `EXPIRED` 时，**没有任何东西会收口占用**。若占用为开区间，则该单元**永久显示为在租**——即使合同已到期。

| 文件 | 现状 | 改为 |
|------|------|------|
| `ScheduledJobs.contractExpiryScan`（`:106`） | 仅 `setStatus(EXPIRED)` + 发 `ContractExpiredEvent` | 追加：按 `endDate` 收口该合同占用；并（建议）生成"到期未续签/未退租"待办，供业务跟进超期占用 |

**这条同时说明**：`EXPIRED` 也必须被纳入"终态"清单，验收 SQL ⑮ 的 `status IN (...)` 需要包含它（见 §11 附录 A）。

#### B2 验收

| 检查 | 方式 |
|------|------|
| 合同生效后有 `contract` 占用行 | 验收 SQL ⑭ + 手工查 `asset_occupancy` |
| 五条路径均无残留未收口占用 | 验收 SQL ⑮；逐条手工走：驳回 / 退租 / 终止 / 续签 / 到期 |
| 续签可正常生效 | 手工：对 `RENEWABLE` 合同执行续签并激活 |
| 双写期无状态分歧 | 验收 SQL ④（`v_asset_lease_status_reconcile`）为空；B0 的漂移日志归零 |
| 并发生效不超租 | 同一单元并发提交两份合同，第二条命中 `EXCLUDE` |

**回退**：关 `ams.occupancy.contract-dual-write` + 执行补偿脚本（对该开关期间写入的 `contract` 占用行按合同状态批量收口/删除）。**补偿脚本必须与 B2 同批交付**——这是"可回滚"的实质要求。

**测试**

- 单测（Mockito 风格，参照 `OccupationServiceTest`）：五条收口路径各 1 例 + 未收口断言；
- 真库集成（参照 `MigrationChainPostgresTest`）：`ContractLifecycleOccupancyPostgresTest`——走完"创建 → 生效 → 续签 → 退租"全链，断言无残留未收口占用。

### B4 · 单元合并（3–4 人日，**必须在对外开放拆分之前交付**）

**理由**（ADR-0021 决策 B S12）：**`merge` 是 `split` 的逆操作**。只交付 `split` 等于交付一条**单向、不可撤销**的高危操作——拆错了只能手工改库。

**改动**

| # | 文件 | 改动 |
|---|------|------|
| 1 | `AssetUnitService.merge(List<Long> unitIds, String reason)` | 新增。前置：同资产/同分区/同 `asset_type`+`usage_type`；全部单元无未收口占用、无 `active` 招租、无未结账单、无生效合同；无抵押。动作：面积与底价相加；源单元软删 + 编码映射；结果标的 ≥1 个有效单元 |
| 2 | `AssetUnitService.canRollback(Long unitId)` | 新增：子单元存在合同 / `active` 招租 / 未收口占用即**不可回滚**（可回滚窗口 = 下游未引用前） |
| 3 | 前端 | 弹窗显式区分「可回滚 / 不可回滚」，不可回滚时禁用并说明原因 |

**验收**：合并后 ⑩⑪ 为空；可回滚窗口判定与下游引用一致。

## 5. 数据回填方案

### 5.1 前置：冲突检测（**必须先做，否则回填会被 `EXCLUDE` 拒绝**）

`ex_occupancy_unit_no_overlap` 是硬约束（`V40:319-331`）。存量合同若存在**区间重叠**，回填会**直接失败**。

```sql
-- 回填前置检查：同一单元上、非终态合同的租期重叠
-- 典型来源：续签未终止旧合同、转租未终止原合同
SELECT a.asset_unit_id,
       c1.contract_no AS c1, c1.start_date, c1.end_date, c1.status AS s1,
       c2.contract_no AS c2, c2.start_date, c2.end_date, c2.status AS s2
  FROM contract c1
  JOIN contract c2
    ON c2.asset_unit_id = c1.asset_unit_id AND c2.id > c1.id
   AND daterange(c1.start_date, c1.end_date, '[)')
    && daterange(c2.start_date, c2.end_date, '[)')
  JOIN asset a ON a.id = c1.asset_id
 WHERE c1.status NOT IN ('voided','terminated','expired')
   AND c2.status NOT IN ('voided','terminated','expired');
```

**处置**：逐条人工裁决——保留哪一份、另一份收口到哪个日期。**不得自动裁决**（ADR-0019 的既有立场：冲突数据由人工核对，不由迁移自动决定）。

### 5.2 回填顺序

```text
1) 跑 §5.1 冲突检查 + ⑯，产出工作清单
2) 人工裁决重叠（改合同状态 / 约定收口日）
3) 跑 INV-2 诊断（v_asset_without_unit）→ 补单元
4) 跑验收 SQL ⑭ → 补 contract.asset_unit_id（B1）
5) 分批回填占用行（open 的按 [startDate, endDate)，已终态的按实际收口日）
6) 跑验收 SQL ⑮ 确认无残留未收口
7) 跑 refreshReconciled 一次性对齐物化列
8) 重放投影：POST /internal/projections/rebuild?context=X
```

**分批**：按 `asset_id` 分片，每片一次事务；失败不影响其他分片（可重入）。

## 10. 风险盯防（条件性 P0）

以下缺陷**在当前代码上不会触发**（合同尚未写占用），但**B2 落地即触发**。把它们单独列出，是为了在 B2 期间**逐条盯防**，而不是等验收失败：

| 缺陷 | 触发条件 | 盯防方式 |
|------|---------|---------|
| D-22 驳回不释放预留 | 启用决策 E 后驳回 | B2.2 单测 + 验收 SQL ⑮ |
| D-23 退租不收口 | 走完退租 | B2.3 + 真库集成测试 |
| D-24 终止作废不收口 | 合同作废 | B2.3 |
| D-25 续签转租不收口 | 续签并激活 | B2.4 手工验证 |
| **D-26 合同到期不收口** | 每日 04:00 到期扫描 | B2.5；验收 SQL ⑮ 的终态集合须含 `expired` |

**通用盯防手段**：B0 的漂移日志——只要它归零并保持归零，说明收口闭合；一旦上升，第一时间定位到是哪条路径漏了收口。
