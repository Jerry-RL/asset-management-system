## 2. 编排分层原则

不同闭环的一致性要求差异极大，**不要一律上 Saga**。三类编排对应三种实现：

| 类型 | 判定 | 实现 | 适用闭环 |
|------|------|------|---------|
| **① 单事务编排** | 全部步骤在**一个**聚合/上下文内，可回滚 | `@Transactional` + 状态机唯一入口 | 占用、自用、处置、评估、盘活 |
| **② 事件编排** | 步骤跨上下文，但**无外部副作用**（不改钱/票/合同），失败可重放 | 领域事件 + 幂等消费（需 outbox，§3.3） | 经营、空置→招租、业财对账、通知 |
| **③ 补偿编排（Saga）** | 含**外部副作用**（已收款、已开票、已迁合同），局部失败需逆序补偿 | 补偿步骤记录 + 逆序补偿 + 失败挂待人工 | **退租、退款、调拨**（仅 3 条） |

判据的关键是"**外部副作用**"：业财导入银行流水失败重放即可；退款若已逆序退回核销却红冲失败，则账票不一致，不可重放，必须补偿。

## 3. 共性机制（一次投入）

### 3.1 编排者与补偿记录

**现状**：跨域多步操作**内联在 Service 中**且无补偿记录。已确认的证据：

```117:119:backend/src/main/java/com/ams/modules/billing/service/RefundService.java
        allocationService.reverseAllocation(order.getPaymentId());
        invoiceService.redFlushByPayment(order.getPaymentId());
        pushVoucher(order);
```

**复核更正**：这三步同处一个 `@Transactional`（`reverseAllocation` / `redFlushByPayment` 的传播均为 REQUIRED），因此**「第二步失败而第一步未回滚」的说法不成立**——DB 变更随事务回滚。真实问题是：

1. **外部副作用不可回滚**：`InvoiceService.redFlush` 在事务内调用第三方电子发票平台（`invoiceAdapter.redFlush`）。第三方成功后若后续步骤失败，事务只能还原本库数据，**第三方已红冲的事实回滚不掉**；
2. **静默不一致**：`RefundService.pushVoucher` 原为 `catch (Exception ignored)`，凭证创建失败时流程继续、退款单仍被置为 `completed` → 「已完成但无冲销凭证」且无痕迹；
3. **无处置入口**：失败后没有任何记录供人工接手。

**方案（已交付）**：`process_step` 表 + 补偿编排，**不引入 Saga 框架**（与 ADR-0002/0013 一致）。交付形态：

```sql
-- V43__process_step.sql（已交付；与设计初稿的差异：列名 compensate_kind、增加 rolled_back 状态）
CREATE TABLE process_step (
    id              BIGSERIAL PRIMARY KEY,
    process_type    VARCHAR(40) NOT NULL,   -- vacate / refund / transfer（当前仅 refund 接入）
    biz_id          BIGINT      NOT NULL,
    step_no         INTEGER     NOT NULL,
    step_name       VARCHAR(60) NOT NULL,
    status          VARCHAR(20) NOT NULL,   -- running/done/rolled_back/failed/manual
    compensate_kind VARCHAR(20),            -- rollback / manual
    payload         TEXT,                   -- 预留，当前未写入
    error           TEXT,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ, created_by BIGINT, updated_by BIGINT,
    CONSTRAINT ck_process_step_status
        CHECK (status IN ('running','done','rolled_back','failed','manual')),
    CONSTRAINT ck_process_step_kind
        CHECK (compensate_kind IS NULL OR compensate_kind IN ('rollback','manual'))
);
CREATE UNIQUE INDEX uq_process_step ON process_step (process_type, biz_id, step_no);
```

**四条实现约束（缺一即失效）**：

1. **步骤记录必须写在独立事务**（`REQUIRES_NEW`）——否则业务回滚会把失败痕迹一起回滚，补偿与排障无从下手。代价是记录先于业务提交可见，故外层失败时**必须**把已成功步骤改判为 `rolled_back` / `manual`（由 `CompensationOrchestrator` 统一负责，业务代码不得自行处理）；
2. **`begin` 必须 upsert 而非 insert**——重试整个流程时同一步骤会再次 begin，insert 会撞唯一键；upsert 复用该行并把状态重置为 `running`、清空 `error`；
3. **补偿策略取自编排声明（内存），不取数据库读回的行**——补偿判决必须依据调用方声明的 `CompensateKind`，而非一次可能不完整的读取；
4. **自动补偿（auto）不实现**：在出现真实可自动化的补偿动作前保持 `rollback`/`manual` 两档，避免造出无人使用的抽象。

**状态语义**（决定"谁负责收拾"）：

| 状态 | 含义 | 谁负责 |
|------|------|--------|
| `done` | 已成功 | — |
| `rolled_back` | 随外层事务回滚，已还原 | 无需人工 |
| `failed` | 步骤失败且无外部副作用 | 重试即可 |
| `manual` | 外部副作用可能已发生，或补偿不可自动执行 | **人工** |

**适用范围**：只对含外部副作用的三条流程建（`vacate` / `refund` / `transfer`）。其余闭环用领域事件即可（§2 编排分层）。**当前仅 `refund` 接入**，退租与调拨待接。

### 3.2 状态机唯一入口与状态常量

**现状**：全库 **60+ 处** `setStatus("字面量")`，只有 `ContractStatus` / `BillStatus` 是常量类。这与 §5 术语表和 ADR-0019 对租控状态的处理方式**自相矛盾**——租控做到了"唯一写入口 + 常量类"，其他域却仍是裸字符串。

**方案**：每个写状态的上下文补一对（**参照 `ContractStatus` 的既有范式，不新造抽象**）：

```java
/** 每上下文一个状态常量 + 一个转移表；禁止 Service 直写 status。 */
public final class OccupationStatus {
    public static final String DRAFT = "draft";
    public static final String APPROVING = "approving";
    public static final String OCCUPIED = "occupied";
    public static final String RELEASED = "released";

    private static final Map<String, Set<String>> TRANSITIONS = Map.of(
        DRAFT,      Set.of(APPROVING),
        APPROVING,  Set.of(OCCUPIED, DRAFT),
        OCCUPIED,   Set.of(RELEASED),
        RELEASED,   Set.of()
    );

    public static void assertTransition(String from, String to) { /* 非法转移抛 CONFLICT */ }
}
```

| 上下文 | 需要的常量类 | 优先级 |
|--------|------------|--------|
| 占用与租控 | `OccupationStatus` / `SelfUseStatus` / `DisposalStatus` / `RevitalizationStatus` | P1 |
| 收费结算 | `RefundStatus`（`BillStatus` 已有） | P1 |
| 发票 | `InvoiceStatus` | P2 |
| 权证与权属 | `EvaluationStatus` / `MortgageStatus` / `TransferStatus` | P2 |
| 风险与合规 | `AlertStatus` / `ComplianceStatus` | P2 |
| 经营计划 | `PlanStatus` | P2 |

**验收**：`rg 'setStatus\("' backend/src/main` 仅命中常量类与状态机内部（同 §14 标准 3 对租控状态的校验方式）。

> 例外：`task` / `notification` 的 status 是纯流程标记（pending/completed），不承载业务不变量，**不强制**状态机。

### 3.3 事件目录补全 + outbox

**现状（已验证）**：全库只有 **2 个**事件类——`ApprovalCompletedEvent`、`PaymentRegisteredEvent`。而 ADR-0013 与 DSD §4.8 都列了 8 个。**通知闭环的"业务事件→推送→待办→处理"实际只通 2 条链路。**

| 事件（DSD §4.8） | 事件类 | 发布点 | 状态 |
|-----------------|--------|--------|------|
| ApprovalCompleted | ✅ 存在 | `ApprovalEngine` | 已实现 |
| PaymentRegistered | ✅ 存在 | 收款登记 | 已实现 |
| BillIssued | ❌ 缺 | `BillService` 出账后 | **待补** |
| BillOverdue | ❌ 缺 | `DunningService.scanOverdue` | **待补** |
| AlertTriggered | ❌ 缺 | `AlertService` 生成记录后 | **待补** |
| DisposalCompleted | ❌ 缺 | `DisposalService.complete` | **待补** |
| ContractExpired | ❌ 缺 | 合同到期扫描 | **待补** |
| AssetTransferred | ❌ 缺 | `TransferService.complete` | **待补** |

**方案**：补 6 个事件类与发布点（发布走 `DomainEventPublisher`，已是 `AFTER_COMMIT` 语义）；消费端幂等键 `(eventId, consumer)`；投递保证见[设计 §12.4](./领域划分与限界上下文设计.md)（`domain_event_outbox`）。

**已交付（P0-8）**：

| 项 | 交付物 |
|---|--------|
| 6 个事件类 | `BillIssuedEvent` / `BillOverdueEvent` / `AlertTriggeredEvent` / `DisposalCompletedEvent` / `ContractExpiredEvent` / `AssetTransferredEvent` |
| 发布点 | `BillService.issueBills`、`DunningService.onLevelUpgraded`、`AlertService.create`、`DisposalService.complete`、`ScheduledJobs.contractExpiryScan`、`TransferService.approve` |
| 投递保证 | `V44` 发件箱 + `OutboxStore`/`OutboxDispatcher`/`EventTypeRegistry` + `EventConsumptionGuard` |
| 消费幂等 | `event_consumption` 台账；`NotificationEventListener` 8 类订阅全部接入 |

**两条必须在实现中守住的约束**（否则退化为缺陷）：

1. **`BillOverdue` 仅在真正逾期时发布**——到期前 L1 提醒（`pre_due_remind`）不是逾期，发布会让下游把「即将到期」统计成「已逾期」；
2. **事件类构造器必须标注 `@JsonCreator` + `@JsonProperty`**，且 `event_id`/`occurred_at` 由 outbox 列承载（`@JsonIgnore` 排除出 payload），重放时经 `restoreIdentity` 还原——**重放前后 eventId 必须一致**，否则下游幂等台账失去作用。

**顺带修复的缺陷**：`DomainEventPublisher` 原用 `@TransactionalEventListener` 默认 `fallbackExecution=false`，在**无事务**的调用点（如定时任务、非事务 Service）事件会被**静默丢弃**。现改为 `true`：无事务时立即分发，且发件箱已落行，分发失败仍可重放。

### 3.4 跨上下文交互收敛

闭环编排落地时，**极易用直读对方 Mapper 的方式实现**——现状已有先例（`AlertService` 读 `ContractMapper`/`BillMapper`，见评审 P0-1）。规则：

1. 编排者只允许依赖**下层的 `port` 包**与**领域事件**；
2. 需要"上层规则做提交前校验"时用**依赖倒置**（[设计 §6.2](./领域划分与限界上下文设计.md) 交互方式 ⑤）；
3. 跨上下文只读投影必须存 `source_version`，可被比对作业发现。

## 4. 逐闭环编排规格

格式：触发 → 步骤 → 状态机 → 一致性 → 补偿 → 已知缺口 → 验收。

### 4.1 闭环 2：空置与盘活（FR-VACANT-001~004）

```text
触发: 单元派生状态 = vacant 且 vacant_since 超过阈值
  1) 识别空置（真源：v_unit_lease_status + asset.vacant_since，由 LeaseStatusDeriver 派生）
  2) 生成盘活任务 RevitalizationTask(pending)          ← createOnVacant
  3) 制定盘活方式（招租 / 处置 / 自用）
  4) 转招租 → 写 lease_listing(status=active)          ← ⚠️ 当前缺失，见缺口 ①
  5) 签约成功 → closeOnLeased → 任务置 signed、清空 vacant_since/vacant_reason
  6) 或转处置 → 闭环 6
一致性: 事件编排；closeOnLeased 幂等（按 (assetId, status in pending/listing) 批量收口）
补偿: 不需要（无外部副作用）
```

| 状态机 | 取值 | 完整性 |
|--------|------|--------|
| `RevitalizationTask.status` | pending / listing / signed | 与 SRS §4.23.9 一致 |

**已知缺口**

| # | 缺口 | 严重度 | 修法 |
|---|------|--------|------|
| ① | **盘活→招租链路断裂**：`updateStatus` 只改状态，不生成 `lease_listing`，"转招租"仍需人工在招租模块另建 | P1 | `RevitalizationService` 调 `LeaseListingService`（依赖倒置：由招租域定义 Port，盘活域注入）；或发布 `RevitalizationDecided(planType=listing)` 事件由招租域订阅建发布 |
| ② | `escalateLongVacant` 以 `asset.lease_control_status = VACANT` 为条件，**未按单元** | P1 | 改为遍历"无生效占用的单元"，用 `asset_occupancy.date_to` 算空置时长（改造清单触点 20） |
| ③ | `updateStatus(id, status)` 裸 `setStatus`，无转移校验 | P2 | 补 `RevitalizationStatus` 常量 + 转移表 |

**验收**：空置超阈值的**单元**（非资产）必存在 pending/listing 任务；签约后任务 `signed` 且 `vacant_since` 为空；转招租后 `lease_listing` 存在 active 记录。

### 4.2 闭环 4：风险与预警处置（FR-ALERT-LC-001~004）

```text
触发: 定时规则扫描 + 业务事件
  1) 规则评估（合同需续签/已到期、账单逾期、抵押到期、占用到期）
  2) 生成 AlertRecord(pending)，emit AlertTriggered    ← ⚠️ 事件缺失，见 §3.3
  3) 指派责任人 → processing + 生成待办 Task
  4) 处置（记录处理说明）
  5) 关闭 closed / 超时升级 escalated → 生成督办任务（FR-PLAN-004）
一致性: 事件编排；同 (ruleId, bizType, bizId) 去重（现有 exists 校验，见 AlertService:96）
补偿: 不需要
```

| 状态机 | 取值 | 与 SRS §4.24.4 对齐 |
|--------|------|-------------------|
| `AlertRecord.status` | pending / processing / escalated / closed | ✅ 一致 |

**已知缺口**

| # | 缺口 | 严重度 | 修法 |
|---|------|--------|------|
| ① | `AlertService` **直读** `ContractMapper`/`BillMapper`/`CertificateService` | P0（评审 P0-1） | 迁出 L0 至 L5 风险与合规；跨域读取改依赖倒置 Port 或投影 |
| ② | `AlertRule` 表存在，但扫描逻辑**硬编码**四类规则，规则表未真正驱动扫描 | P1 | 规则评估器按 `AlertRule.rule_type` 分发；硬编码逻辑降级为默认规则种子 |
| ③ | 无 `AlertTriggered` 事件 → 通知闭环无法订阅 | P1 | 补事件类（§3.3） |

**验收**：每条启用的 `AlertRule` 可触发生成记录；关闭必填处理说明；升级生成督办任务且留痕。

### 4.3 闭环 7：临时占用（FR-OCC-001~004）

```text
触发: OccupationOrder.create
  1) 草稿
  2) 提交审批(approving) + **预留单元**（reserve，biz_status=reserving）   ← ⚠️ 当前未接预留态
  3) 审批通过 → occupied + occupy(unit, 'occupation') / 驳回 → releaseRow
  4) 解除（登记腾空日）→ released + 区间收口
  5) 单元派生状态自动归位（无需独立步骤）
一致性: 单事务编排（同上下文）
补偿: 不需要（预留行由驳回路径收口）
```

| 状态机 | 取值 | 与 SRS §4.24.6 对齐 |
|--------|------|-------------------|
| `OccupationOrder.status` | draft / approving / occupied / released | ✅ 一致 |

**已知缺口**

| # | 缺口 | 严重度 | 修法 |
|---|------|--------|------|
| ① | **未接预留态**（ADR-0020 决策 E）：审批期不写占用 → 与闭环 7 并存的两个申请可同时签同一单元 | P1 | 触点 28：提交审批调 `reserve`，通过调 `activateBySubject`，驳回调 `cancelReservation` |
| ② | 仍走旧 `LeaseControlService.transition`（改造清单触点 5） | P1 | 改 `AssetOccupancyService.occupy/release` |
| ③ | 解除链的"腾空日"语义未定义（取当天 or 实际腾空） | P2 | 表单增加实际腾空日；缺省取当天 |

**验收**：并发提交两个同单元占用单，第二个提交即被拒（`EXCLUDE`）；解除后单元派生状态回 `vacant`。

### 4.4 闭环 8：业财一体（FR-FIN-001~005）

```text
触发: 银行流水导入 / 收款到账 / 月结
  1) importFlow 导入银行流水
  2) 自动匹配（金额 / 日期 / 备注）
  3) 未达账项清单（unmatchedFlows / unmatchedPayments）+ rematchUnmatched 重匹配

  6) createVoucher + pushVoucher 推送凭证（推 ERP）
  7) 月结：lockMonth（锁定后不可改，unlockMonth 需留痕）
一致性: 事件编排；匹配幂等（按流水号 + 金额 + 日期）
补偿: 不需要（重匹配即可）；凭证推送失败需重试（缺口 ①）
```

**代码现状**：`ReconcileService` 13 个公开方法，覆盖上述全部步骤，**含未达账项**——闭环 8 的代码完成度高于文档描述。

**已知缺口**

| # | 缺口 | 严重度 | 修法 |
|---|------|--------|------|
| ① | `pushVoucher` 无幂等键与失败重试；失败后 `FinanceVoucher` 停留 `pending` 无告警 | P2 | 幂等键 `(bizType, bizId, period)` + 重试 + `pending` 超时告警 |
| ② | `FinanceMonthClose` 与"收入确认"的关系未文档化 | P2 | 明确：收入确认以月结锁定为界，锁定后不可追加凭证 |
| ③ | 月结锁定未校验"未达账项已清" | P2 | `lockMonth` 前置校验：`unmatchedFlows`/`unmatchedPayments` 为空或已标注 |

**验收**：导入 N 笔流水后 `unmatchedFlows` 与 `unmatchedPayments` 两侧口径一致；月结锁定后不可改；凭证推送失败可重试且不重复。

### 6.2 全局一致性 SQL（与设计 §14 合并执行）

```sql
-- ① 合同行面积守恒（INV-11，闭环 A）
SELECT c.id, c.lease_area, SUM(l.lease_area) AS line_area
  FROM contract c JOIN contract_line l ON l.contract_id = c.id
 GROUP BY c.id, c.lease_area
HAVING ABS(c.lease_area - SUM(l.lease_area)) > 0.005;

-- ② A1 不变量：占用面积 == 单元面积（闭环 A/7/13）
SELECT count(*) FROM asset_occupancy o
  JOIN asset_unit u ON u.id = o.asset_unit_id
 WHERE u.area <> o.area;

-- ③ 退款冲正完整性（闭环 10）：已完成的退款必须已红冲且已推凭证
SELECT r.id, r.status,
       EXISTS (SELECT 1 FROM invoice i WHERE i.payment_id = r.payment_id
                AND i.status = 'red_flushed') AS has_red_flush,
       EXISTS (SELECT 1 FROM finance_voucher v WHERE v.biz_type = 'refund'
                AND v.biz_id = r.id) AS has_voucher
  FROM refund_order r
 WHERE r.status = 'completed'
   AND (NOT EXISTS (SELECT 1 FROM invoice i WHERE i.payment_id = r.payment_id
                     AND i.status = 'red_flushed')
     OR NOT EXISTS (SELECT 1 FROM finance_voucher v WHERE v.biz_type = 'refund'
                     AND v.biz_id = r.id));

-- ④ 补偿未完成步骤（闭环 10/A）
SELECT process_type, biz_id, step_no, step_name, status, error
  FROM process_step WHERE status IN ('failed', 'manual') ORDER BY created_at;

-- ⑤ 事件投递健康度（闭环 12）
SELECT status, count(*) FROM domain_event_outbox GROUP BY status;   -- dead 必须为 0

-- ⑥ 通知重复投递（闭环 12）
SELECT event_id, consumer, count(*) FROM notification_consumption
 GROUP BY event_id, consumer HAVING count(*) > 1;

-- ⑦ 发票勾稽上限（闭环 9）
SELECT i.id, i.amount, SUM(r.amount) AS reconciled
  FROM invoice i JOIN invoice_reconcile r ON r.invoice_id = i.id
 GROUP BY i.id, i.amount HAVING SUM(r.amount) > i.amount;

-- ⑧ 空置督办按单元（闭环 2）
SELECT v.unit_id, v.asset_id, MAX(o.date_to) AS last_released
  FROM v_unit_lease_status v
  LEFT JOIN asset_occupancy o ON o.asset_unit_id = v.unit_id
 WHERE v.derived_status = 'vacant'
 GROUP BY v.unit_id, v.asset_id
HAVING MAX(o.date_to) < CURRENT_DATE - INTERVAL '180 days'
   AND NOT EXISTS (SELECT 1 FROM revitalization_task t
                    WHERE t.asset_id = v.asset_id
                      AND t.status IN ('pending', 'listing'));
```
